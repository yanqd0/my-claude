---
allowed-tools: Read Write
description: 生成色彩合理、分组清晰的 mermaid 图。自动推测图类型，支持上下文分析和交互确认。
---

根据用户描述或上下文，生成一张或多张 mermaid 图。支持一个可选参数：`<description>`，描述对什么画、怎么画。

## 执行步骤

1. 确定绘图对象和内容：
   - **有 `<description>`**：按描述绘制。
   - **无 `<description>`**：回顾对话上下文中适合可视化的内容（如架构、流程、状态机、数据关系、时序等），整理出一份或多份绘图内容的简要说明，**逐一**通过交互提示请用户确认"是否按此内容绘制"，用户确认哪些就画哪些。
2. 推测图类型：根据绘图内容自动选择最合适的 mermaid 图类型，不二次确认。若用户在 `<description>` 中明确指定了类型，则遵守用户要求。

   **类型选择指南**（先判断核心叙事维度，再选类型）：

   | 核心叙事 | 图类型 | 代码阅读场景 | 技术介绍场景 |
   |---------|--------|-------------|-------------|
   | 结构关系 | **flowchart** | 模块依赖、调用链、条件分支、管道步骤 | 系统架构、部署拓扑、算法流程 |
   | 块结构 | **block** | 系统方块图、组件层次总览 | 部署架构块图、模块划分简图 |
   | 交互顺序 | **sequenceDiagram** | 跨服务 API 调用、消息传递、中间件链路 | 认证流程、协议握手、微服务通信 |
   | 状态转移 | **stateDiagram-v2** | 订单/任务/连接等有状态实体的生命周期 | TCP 状态机、进程状态、Promise 状态、CI 流水线阶段 |
   | 类型层级 | **classDiagram** | 类继承/组合、接口实现、struct 嵌套 | 设计模式结构、框架核心类型、ORM 模型 |
   | 数据实体 | **erDiagram** | Schema 定义、ORM 模型中的表关联与外键 | 数据库设计、微服务数据模型、API 嵌套结构 |
   | 进度/计划 | **gantt** | 不适用（gantt 面向计划而非代码） | 功能开发排期、版本路线图、里程碑节点 |
   | 时间线 | **timeline** | git log 可视化、文件修改编年 | 技术演进史、版本重大变更年表、系统关键事件 |
   | 用户旅程 | **journey** | 用户操作在代码中的追踪路径、开发者工作流 | 用户引导流程、功能体验路径、满意度分阶段分析 |
   | 占比分布 | **pie** | 目录文件类型占比、测试覆盖/错误类型统计 | 流量分布、资源分配、语言/框架占比 |
   | 量化对比 | **xychart** | benchmark 结果、性能指标版本间对比 | 框架性能横向对比、QPS/延迟/资源占用柱状图 |
   | 集合关系 | **venn-beta** | 功能重叠分析、模块依赖交集 | 技术方案差异与交集、能力覆盖重叠、概念关系 |
   | 分支拓扑 | **gitGraph** | git 分支合并历史、rebase vs merge 差异 | 分支策略（GitFlow/Trunk-based）、发布流程 |
   | 因果分析 | **ishikawa-beta** | Bug 根因追溯、性能瓶颈分解 | 问题分解、故障模式归类 |
   | 知识层次 | **mindmap** | 项目目录结构、模块职责划分 | 技术体系全景、知识点梳理、功能拆解脑图 |

   选择优先级：结构 > 交互 > 状态转移 > 时间/分布 > 量化对比。当单一图类型无法覆盖时，优先拆分为多张不同类型的图。

   **图类型语法名对照**：flowchart（用 `flowchart` 而非已废弃的 `graph`）、sequenceDiagram、stateDiagram-v2（用 `stateDiagram-v2` 而非旧版 `stateDiagram`）、classDiagram、erDiagram、gantt、timeline、journey、pie、xychart、venn-beta、gitGraph、ishikawa-beta、block、mindmap。
3. 执行 `Read` 读取目标文件（若有），了解上下文以画出更准确的图。
4. 生成 mermaid 代码，先输出预览，得到用户确认后再写入文件（写入策略见步骤 7）。
5. 大小控制：
   - flowchart / sequenceDiagram / classDiagram：估算节点数和边数，超过 30 节点或 40 边时提示用户选择**继续画一张大图**、**拆分为多张小图**、或**精简内容**。
   - gantt / timeline：以条目数衡量，超过 15 条时提示。
   - mindmap：超过 4 层或 25 节点时提示。
   - pie：超过 8 个扇区时提示（过多扇区降低可读性）。
   - 若用户选择拆分，按逻辑边界（子域、阶段、层级等）设计每张子图的内容范围，逐一确认后绘制。
6. 格式规范：
   - 使用双引号包裹含空格或特殊字符的节点标签和边标签。节点标签中需要换行时，使用 `<br/>` 而非 `\n`。节点 ID 不含空格即可。
   - 节点 ID 使用简洁的英文或拼音标识，节点标签使用中文（除非用户要求英文）。
   - 使用 `classDef` 按语义分组定义统一样式类，再通过 `class` 应用到节点。分组维度示例：按系统/角色、按层级（前端/后端/数据）、按状态（正常/异常/待定）、按模块。
   - 颜色选择原则：同一分组使用同色系，不同分组色相区分明显；背景色优先低饱和度（护眼），边框色同色系深色；文字色用深色保证可读性。避免使用超过 5 种主色相。
   - flowchart 必须指定 `TB`（自上而下）或 `LR`（从左到右）方向。
   - 使用 `subgraph` 对相关节点进行分组，subgraph 标题用中文简要概括分组含义。
   - 节点形状按语义选择：`[...]` 矩形（实体/组件）、`(...)` 圆角（开始/结束）、`[(...)]` 圆柱（数据库）、`{...}` 菱形（决策）、`[[...]]` 方形（用户操作）、`((...))` 圆形（连接点）。
   - 图的标题使用 YAML frontmatter 格式（源码中真实换行）：
     ```mermaid
     ---
     title: 中文标题
     ---
     flowchart TB
     ...
     ```
     若渲染器不支持 frontmatter，则在图中用注释 `%% 图标题：xxx` 标注。
   - 不生成单独的 README 或说明文件，直接把 mermaid 代码块嵌入到回复中供用户预览。
7. 写入文件：
   - 默认不写入文件，仅在回复中展示 mermaid 代码块。
   - 若用户要求写入文件，写入到用户指定的路径；若用户未指定路径，写入到当前对话相关的 `.md` 文件中，或按用户指示操作。
8. 多图处理：若有多张图，每张图的 mermaid 代码块前用 Markdown 标题或加粗文本标注图名，方便区分。
