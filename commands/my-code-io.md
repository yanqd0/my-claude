基于给定代码入口，分析并撰写一篇多章节的技术介绍文章。支持一个参数：`<entry>`，为文件路径、文件夹路径或一段功能描述。

## 执行步骤

1. 解析入口：
   - 若 `<entry>` 是存在的文件或文件夹路径，直接作为分析入口。
   - 若 `<entry>` 是一段描述（非路径），在当前项目中搜索匹配的代码位置；若匹配结果模糊，列出候选请用户确认。
   - 若 `<entry>` 为空，回顾对话上下文，尝试从之前涉及的文件中推断入口，并以交互提示请用户确认。
2. 读取与分析：
   - 从入口出发，递归追踪引用和依赖，梳理代码全貌。分析维度包括但不限于：
     - **整体架构**：模块划分、分层结构、目录职责。
     - **业务内容**：核心领域概念、业务流程、关键规则。
     - **数据流**：数据从哪来、经过哪些处理、到哪去、持久化方式。
     - **调用关系**：函数/模块间的调用链、上游下游、同步异步。
     - **关键接口**：对外暴露的 API、CLI 入口、配置文件格式。
     - **设计模式与抽象**：重要的基类/接口、工厂、策略、中间件等。
     - **扩展点与配置**：插件机制、开关、环境变量等。
   - 优先读取核心逻辑文件，跳过第三方依赖、生成代码、二进制文件。
3. 规划文章结构：
   - 根据分析结果，设计文章大纲（章节标题 + 各节要点），通过交互提示请用户确认大纲后再开始撰写。
   - 标题层级最多 5 层（`#####`）。
   - 内容排序：分析框架可大致确定，但输出结果不应千篇一律。根据实际重要程度调整章节顺序，重要的放前面。总体原则：业务优先于技术，架构优先于细节；但非常关键的技术细节可提前到靠前位置着重写。
   - 章节取舍：分析后认为不重要或内容不足的章节，在篇幅紧张时可直接省略，不为了保留章节结构而填充冗余内容。
   - 若预估文章超过 300 行，提示用户选择：**合并为一篇**、**拆分为多篇**（每篇独立保存）。
4. 撰写文章：
   - 语言：中文为主，代码符号、类名、函数名、关键概念保留英文原文。语言风格准确严谨，避免风趣幽默或口语化表达。
   - 读者定位：具备基本软件技术常识（变量、函数、文件等概念），但不了解该项目的技术栈和业务背景。开篇先解释"这个项目是干什么的"，逐步深入。
   - 说明"为什么"而非仅"是什么"：解释设计意图、业务背景，帮助读者建立心智模型。
   - 引用关键代码片段（不超过 25 行），用 Markdown 代码块并标注语言。代码前加一句解释这段代码做了什么。
   - 避免大段粘贴代码，优先用简洁的描述 + 短小的关键片段。
   - 若某个模块粒度过大（预计该模块的章节将超过 80 行），提示用户：将该模块拆分为独立文章单独撰写，原章节仅保留概括性描述和指向独立文章的链接。
5. 插入图表：
   - 在适合可视化的位置（架构概览、核心流程、数据流向、状态变迁等），调用 `/my-mermaid` 生成 mermaid 图。
   - 若内容不适合 mermaid（如目录树、简单对照表、ASCII 友好的布局），用代码块 + ASCII 绘图代替。
   - 每张图前用文字说明图的内容和如何阅读。
6. 保存文章：
   - 在 `/tmp/claude/articles/` 下创建目录（若不存在）。
   - 文件名与文章标题相同（中文即可），后缀 `.md`。若有多篇，每篇独立命名。
   - 同时将完整文章内容打印输出到对话中。
7. 多篇拆分（仅在步骤 3 中用户选择拆分时触发）：
   - 每篇聚焦一个主题（如"架构概述"、"核心流程"、"数据与存储"等），各有独立的标题和目录。
   - 每篇开头列出系列中其他文章的链接。
   - 每篇单独确认大纲后再撰写、保存。

## 约束

- 执行全程不得修改当前工作目录下（递归）的任何文件，也不得在当前工作目录下（递归）写入新文件。文章仅输出到对话和 `/tmp/claude/articles/`。

## 文章格式规范

- 文章标题用 `#`（一级标题），章节用 `##` 至 `#####`。
- 代码块标注语言：```` ```python ````、```` ```javascript ```` 等。
- 代码块中不翻译注释，保持原样。
- 术语首次出现时可用 `（英文原文）` 标注，后续直接用中文或英文均可。
- 不使用 emoji。
- 不生成额外的 README 或说明文件。
